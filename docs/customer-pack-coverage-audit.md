# 顧客パックの取得・利用範囲の監査

監査日: 2026-11-10。対象: Copilotプロンプト、全画面のデータ入口、パックスキーマ、取り込み、共有検証器、任意拡張、Project別作業データ。

## 監査の前提（深掘りの4点と書き直した依頼）

1. 専門家が追加で行うこと: プロンプトの読み比べではなく、アプリの全データ入口（画面・スキーマ・任意拡張）から必要データを逆引きし、取得指示と1項目ずつ突き合わせる。取得できなかった項目を「欠落」と「意図的な除外」に分け、除外理由を明文化する。検査合格と網羅を区別する。
2. 最も生の素材: [src/data/schema.ts](../src/data/schema.ts)・[docs/pack.schema.json](./pack.schema.json)・拡張スキーマ、各画面のデータ参照コード、[Copilotプロンプト原文](./copilot-customer-pack-prompt.md)、Microsoft 365 CopilotのWeb検索に関する公式文書。実際のCopilot回答は添付がないため素材にできない。
3. 手法とツール: スキーマのプロパティ全列挙とプロンプト（日英）の機械照合、Zod/共有verifyによる取り込み検査、合成回答を使った単体テスト（Vitest）、画面テスト（Playwright）、`schema --check`。
4. 第三者による検証: 型検査・テスト・スキーマ差分検査の実行結果、Microsoft公式文書、そして最終的には所有者が実テナントで実行した回答と出典URL（この監査の範囲外）。

書き直した依頼: 「BASの全データ入口から必要データを逆引きし、Copilotプロンプト（日英）がスキーマの全フィールドを要求しているかを機械照合せよ。欠落は修正し、除外は理由を書け。公開Web調査が指示されているか、出典URL・確認日・未取得理由が保存・表示されるかを確認せよ。結果は型検査・単体/画面テスト・スキーマ差分検査で示し、実テナントで未検証の点を明記せよ。」

実行結果（2026-11-10 再実行）: スキーマのプロパティ89件のうち、日英プロンプトの両方で要求されていないものは8件（person.portraitのskin/hair/hairColor/glasses/beard/outfitHue、illustrationのmotif/hue）。いずれもBASが表示用に生成する装飾で、プロンプトに「書かない」と明記されている（個人の容姿を推測させない）。未説明の欠落は0件。型検査、単体テスト31ファイル499件、`pack-import` 画面テスト2件、`schema --check` が合格。

要求定義書への記載: FR-308〜FR-310・AC-888〜AC-897（[要求定義書 §3.8](requirements-definition.md#38-顧客パックの取得範囲出典取得報告fr-308fr-310)）、実テナントでの確認はTODO-010。上記の照合は単体テスト「every property of docs/pack.schema.json」として常設した（プロンプトから1項目消すと失敗することを確認。単体テストは501件合格）。

## 結論

旧プロンプトではBASの全取得対象を網羅していなかった。また、スキーマ検査合格から「必要なデータが揃った」とは判定できなかった。以下を修正した。修正後も、公開Webだけで非公開データを取得することや、企業の全資料を漏れなく検索することは保証しない。

| 発見事項 | 修正 |
|---|---|
| 「指定資料だけ」を根拠にしており、インターネット調査を依頼していなかった | 公開Web調査と、承認済み社内資料との統合を日英の別プロンプトに分離。公式サイト・IR・拠点・製品・導入事例・ブランド等を明示 |
| 出典にURL・確認日・資料内の位置を保存する項目がなかった。発行日不明の資料を落とす必要があった | sourceにurl/accessedDate/locator/originを追加。publishedDateを任意化。カード表示・保存・再読み込み・書き出しまで維持 |
| brand/dataCatalog/glossary/graph/architecture/coreObjectの取得指示がなかった | 全6拡張の出力形・列挙値・取得範囲・出典の記録方法を追加 |
| 任意拡張の不正データが検査を通り、画面で無視され得た | 実際の画面と同じスキーマで形式検査。graphの未知参照も拒否 |
| パックのdataCatalogはデモ用の初期化だけで、取り込んだProjectで使用されなかった | パック非同期読み込み後に、対象Projectのカタログとして解決。明示的な別途取り込み・削除を優先し、別Projectと混ぜない |
| 未取得項目・Web調査失敗の機械可読な記録と画面表示がなかった | extensions.collectionを追加。全24区分・状態・不足フィールド・出典・理由・次の取得方法を表示。旧パックは未報告 |
| 不足PARTや矛盾を通知しても、残りがスキーマに合えば取り込めた | 不足・矛盾・利用回答内の壊れたJSONを取り込みエラーに変更。拡張をPART間で結合可能に |
| 最適化の行列サイズ・地域順、フローの参照種類が検査されていなかった | plants×regionsの整合・工場参照・地域ID重複・フロー参照種類を検査。flows/optimizationにもsourceIdsを追加 |
| 不明な生産能力を0と誤認したり、依存エンティティを成立しないまま出力する危険があった | 未知は推測・平均・0で埋めず、必須値不足と依存による除外を明示 |

## データ利用箇所から逆引きした範囲

スキーマの正本は[基本パック](../src/data/schema.ts)、拡張の正本は[共通拡張](../src/data/extensionSchemas.ts)・[グラフ](../src/modules/graph/extensions.ts)・[ブランド](../src/modules/ops/brand.ts)・[カタログ](../src/modules/usecases/catalogSchema.ts)。全画面の入口は[画面定義](../src/app/modules.ts)。

| 画面・利用箇所 | 顧客パックから取得する素材 | 公開情報だけでは不足する主なもの |
|---|---|---|
| 起動選択・概要・会社情報 | company、source、各kind | 企業・Project登録は端末側の作業データ |
| 地図・一覧・詳細・業務チェーン | regions、site、person、customer、product、deal、deliverable、invoice、supplier | 工場能力・価格・担当者・受注・納期・請求 |
| 課題・関係・施策計画 | issue、cause、solution、kpi、initiativeと相互参照 | 評価点・基準/現状/目標・費用/効果・進捗・依存 |
| 業務フロー | flows、仕入先/拠点/顧客/地域 | 同じ期間・単位の物量実績 |
| 最適化 | optimization、工場と地域順 | 能力/需要/費用/CO2/リードタイム/現配分の全行列 |
| 関係グラフ | graph（関係意味・追加関係・Twin・データ/制御フロー・層・KPI段階） | 実際のシステム対応・制御関係 |
| 3D/Twin | 基本エンティティ、architecture、coreObject | AsIs構成、承認されたToBe、比較根拠。省略時の表示は実測の証明ではない |
| データカタログ | dataCatalog、パック/ユースケースから導出したBAS項目 | 社内の実データ辞書・列・ドメイン。実データベースへの接続ではない |
| 議論画面の用語切替 | glossary | 企業固有の業務/IT用語 |
| ブランド画面・全体テーマ | brand | 明示された色・フォント・利用条件。ロゴ画像ファイルはJSON取り込み対象外 |
| ホーム・成果物・分析・議論・ユースケース | パックは分析対象や候補の素材として使用 | 編集済み分析・OKR・決定/アクション・承認・登録ユースケースは別のProject作業データ |
| ワークスペース・ボード・プレゼン | パックの項目を表示/参照 | レイアウト・ストローク・シナリオ・録画等はアプリで作成・別保存 |
| AI・連携・設定・データ管理 | 現在パックとメタデータ、任意の参照 | 接続設定・資格情報・利用者設定を公開調査で取得・生成しない |

パックはアプリ全体のバックアップ形式ではない。Project作業データは既存の手入力・出力/復元経路を使い、取り込みで既存の人の判断を上書きしない。

## 取得報告の判定

全24区分: company, regions, source, site, person, customer, product, deal, deliverable, invoice, issue, cause, solution, kpi, initiative, supplier, flows, optimization, brand, dataCatalog, glossary, graph, architecture, coreObject。

- 「あり」はデータの存在だけ。「complete」は取得者の申告で、真実性の機械検証ではない。
- `partial`は一部取得、`unavailable`は未取得、`notApplicable`は理由付きの対象外。
- 完了申告にはデータ・出典・不足なしが必要。各区分の重複や欠落は拒否。
- 出典は実際に開けるか、対象企業/期間/連結範囲/単位が一致するかを所有者が確認する。
- flows/optimizationに出典がない旧形式は互換性のため警告。新プロンプトはsourceIdsを要求する。
- 既知の6拡張と取得報告を検査する。将来/第三者の未知拡張に利用可能性を保証しない。

## 外部サービスの条件と限界

[Microsoft公式説明](https://learn.microsoft.com/copilot/plan/manage-public-web-access)によると、Web検索は管理者・利用者設定に依存し、プロンプトや参照資料からBing検索語が作られ得る。このため公開調査には社内資料を渡さず、別チャットで実施する。プロンプトはポリシーを変更できない。Microsoft 365社内検索も契約・権限に依存する。

この監査では顧客資料を外部送信せず、Microsoft 365 Copilotの実環境への問い合わせも行っていない。ユーザーが試した実際の回答・顧客パックは本依頼に添付されていないため、その内容の個別監査は行っていない。公式資料とローカル実装・合成テストデータを検証対象とした。実テナントでの検索網羅率と回答の事実性は未検証であり、対象資料一覧・公開URL・未取得一覧による所有者確認が必要。
